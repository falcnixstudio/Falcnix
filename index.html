What was actually wrong

  • Hero image shipped as a 1.7 MB PNG at 1200px wide, displayed at 360px. Seven product images repeated the pattern: 9.2 MB of PNG for 1.6 MB of visible JPEG quality.
  • Render-blocking CSS — 440 KB across two files loaded before first paint, including a plugin stylesheet where a third of the selectors were never used on the page.
  • 604 KB of JavaScript in the critical path: jQuery, a slider library, a theme bundle and a visitor-tracking script, all parsed before the page could respond.
  • No dimension attributes on images, so the layout reflowed as each one decoded.

What changed

  • Images resized to their real display width, converted to JPEG at quality 78, lazy-loaded below the fold, with explicit width/height on every one.
  • Hero image preloaded; every other image deferred.
  • CSS split into critical (inlined) and deferred; unused plugin CSS dropped.
  • Slider and tracker scripts removed from the critical path; the theme bundle deferred.
  • Result: 8 requests, 61 KiB, nothing blocking the first paint.

What this is, precisely

This is a synthetic store page built to reproduce a common WooCommerce failure pattern: full-size PNGs, stacked plugin CSS, and a slider on the critical path. It is not a client site, and no client data appears anywhere on this page. The numbers come from the saved Lighthouse JSON, run on the same machine, same Chrome build, same throttling settings — mobile form factor, simulated slow 4G — before and after the rebuild. Both reports are published unedited.
